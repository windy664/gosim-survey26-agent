# python-pro —— participant-agent-protocol-v4 的高分参考智能体

[English README see README.md](README.md)

这是 GOSIM survey26 望远镜巡天赛题的一个高分示例智能体，用来展示"认真写的规划器 + 放在关键位置的几次大模型调用"能做到什么程度。只用 Python 标准库；运行时只用协议给智能体的信息（星表、公开评分配置、公报、预报、自己的观测结果）和选手套件里公开的引擎代码，从不读取卡片文件。

## 成绩（本地引擎，Kimi `k3`）

| 卡 | 套件 baseline | python 示例 | **python-pro** |
|---|---:|---:|---:|
| 练习卡 α | 3,617 | -- | **7,127 / 7,151** |
| 练习卡 β | 4,122 | -- | **6,106 / 6,344** |
| 练习卡 γ | 4,030 | -- | **6,749 / 6,814** |
| 练习卡 δ | 3,047 | -- | **6,474 / 6,268** |
| 本地卡 L1 | -- | 4,459 | **6,225** |
| 本地卡 L2 | -- | -- | **6,411** |

练习卡各跑两次，固定搜索力度（`PRO_FIXED_LEVEL=0`），避免繁忙的电脑改变规划；L1/L2 用 `run_local.py` 和正常的 900 秒墙钟各跑一次。正常墙钟下，练习卡 α 得 7,198 分，在一台负载很重的机器上 605 秒跑完。两次运行的差别主要来自仪器故障报告的时机。作为参照：2026-10-03 平台练习榜上单卡最好成绩约 7,400–7,900，所以它是一个强的起点，不是天花板。

## 大模型用在哪里（每晚两个环节，付费报告前再加一次）

每晚开始时，智能体在后台同时发起两次调用：

1. **夜间计划**（自然语言理解、计划自适应）：模型读今晚的预报和当前公报，回答 `{"bad_night", "avoid_directions"}`。`bad_night` 决定今晚要不要花一小时曝光去救暗弱的必选目标（坏天气就留到更好的夜晚）；`avoid_directions` 让规划器整晚避开这些方位。只接受公报或预报里确实点名的方位。
2. **故障复核**（数据解析、行动决策）：模型读智能体自己逐小时的质量表（E = 质量水平 / 档位水平、天空质量 scale、晴夜常见水平、报告历史），回答 `{"fault_likely": 0..1}`。今晚的付费报告听它的：概率低时，不允许只凭逐小时的 E 信号付费探测（只有"连续三晚偏低"的规则还能报告）；否则规则的付费探测照常进行，并先经过下面的模型确认。（`PRO_MODEL_FREE_PROBE=1` 还会在概率高且天空质量明显下降时用一次免费探测；它在练习卡上把免费额度花在了没公告的天气上，所以默认关闭。）

每次**付费**故障报告（报错要扣 150 分）之前，模型先看证据，可以否决。

调用不会拖住巡天：它们在后台线程里跑，每晚开始时只在墙钟允许的范围内等待答案（38 夜的卡最多约 20 秒；长卡更少，晚到的答案到了再用）。任何失败、超时或格式不对的答案，都保留规则给出的默认值。

## 规划器为什么强

1. **一次搜索同时决定指向、光纤、时长、项目**，目标是 `收益 − λ·T`。收益按每个目标"超过它目前最好成绩的部分"计算（只算最好的一次曝光）；λ 是望远镜时间的价格，跟随最近的最好收益率，并按赛季时间的紧张程度缩放。
2. **往哪里指**：以最值钱的 12 个目标为中心（每个都试着放在 16 根光纤上），再加上剩余科学价值最密的 20 块天区，最后用小步平移微调。
3. **必选目标**按达到 0.5 的概率加奖励，并且等到接近它一生中最好的天空条件（以及不是预报坏天气的夜晚）才花一小时去救。
4. **用饱和命中判断项目档位**：饱和命中能精确看出项目倍率，所以能判断声明的项目是否匹配；档位水平按这些命中拟合，而不是跟着质量走（仪器故障会压低质量，但不影响档位）。
5. **仪器故障**：天气同时压低质量和档位，故障只压低质量。`E = 质量 / 档位` 持续偏低就报告，先用免费误报额度，再谨慎地用付费探测。地震要特别处理：参赛文档说明地震也会降低仪器效率，损失逐夜减弱，而且举报不能修复。所以地震公告出现后的 12 小时内不探测；地震影响可能还在的期间，只有 E 比之前几小时又明显下了一个台阶时才探测。在 12 张本地卡上，单这一条就省下了大部分原本浪费在地震上的免费探测（总分 +0.9%）。
6. **隐藏的指向偏差（Hard mode 卡）**：参赛文档说明这类卡会给每次指向叠加一个固定、不公布的偏差。智能体在按光纤间距缩放的网格上给候选偏差打分（最优点落在边缘时自动扩大范围），根据哪些目标命中、哪些落空反推偏差，并用"期望指向 − 偏差"下指令。
7. **观测请求**按全有全无的价值分摊到每个还差的目标上（包括以前已经观测过的目标：只有请求窗口内的曝光才算）。
8. **按公平时钟控制节奏**：平台只计智能体回合内的标准化 CPU 时间（等待不计），另有每卡实际时间上限。智能体用 `time.process_time` 测自己每次决策的 CPU 时间，与 `wallclock.remaining_real_cpu_seconds` 按剩余决策数摊开后的预算比较，同时留意实际时间上限（`wall_remaining_seconds`）；只发 `remaining_seconds` 的旧版运行器按实际时间控制。

## 配置（.env）

```
OPENAI_API_KEY=sk-...                            # 必填（也认 KIMI_API_KEY）
OPENAI_BASE_URL=https://api.kimi.com/coding/v1   # 默认；中国大陆以外账号用 https://api.kimi.ai/coding/v1
OPENAI_MODEL=k3                                  # 默认
```

没有 key 时，程序启动即退出并提示 `missing API key: set OPENAI_API_KEY`；`OBSERVER_MODEL_DISABLED=1`（选择「本次不提供模型」或 `survey26 eval start --no-model` 的评测由平台设置）：此时不需要 key，智能体只用规则运行，便于对比有无大模型的表现。在平台上，`OPENAI_BASE_URL` / `OPENAI_API_KEY` 会自动注入。`k3` 只接受默认温度，所以客户端不发送 temperature。

## 本地运行

```bash
python3 ../_local/runner/run_local.py --inherit-env --card ../_local/cards/L1 --agent "python3 agent.py" --agent-cwd .
python3 pack_agent.py --out ../python-pro-agent.zip
```

`planner.py` 和 `agent.py` 顶部的每个常数都可以用 `PRO_<名字>` 环境变量覆盖（例如 `PRO_LAMBDA_FRAC=0.5`）。`PRO_FIXED_LEVEL=0` 固定搜索力度，在繁忙的机器上做对比更可复现（平台上用的是自适应节奏）。

## 你还可以在哪些地方超过它

- **更快发现仪器故障。** 故障可能让质量大幅下降，每晚没报告的损失可能超过一次付费探测。可以考虑专门的诊断曝光，把故障和没公告的天气分开。
- **公告天气下的项目选择。** 项目不匹配主要集中在全天天气公告的时段。
- **赛季级调度**：把暗弱的必选目标安排到最好的夜晚。
- **被重做的不完整曝光。** 大约十分之一的光纤时间花在了后来被同一目标更长曝光取代的曝光上。`PRO_PARTIAL_DISCOUNT<1` 会对赛季计划预计会做完的目标打折计算不完整曝光；它在四张练习卡上有帮助，在另外八张卡上反而变差，所以默认关闭。
- **更好地用大模型**，例如让它读整周预报，规划哪些夜晚去观测哪片天区。
