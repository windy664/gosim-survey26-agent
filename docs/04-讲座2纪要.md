## 1. 材料与本地环境

- 平台「资源」页 →「下载全部示例」zip：`docs/`（指南）、`local-cards/`（L1–L4 本地卡）、`runner/`（本地裁判）、`python/` `rust/` `typescript/` 三语示例。
- 本地卡存在的理由：线上无法把天气数据发给选手调试，本地卡含真值，可完全离线复现得分。
- 先 `python3 verify_engine.py` 确认引擎全 OK；再跑：
  `python3 run_local.py --card L1 --agent "python3 agent.py" --agent-cwd ../python`
  （转写里的 `--cards ../local_cards/l1` 与实际 CLI 不符，以 `run_local.py --help` 为准）
- 讲座演示的 L1 参考分：**total ≈ 4566**（漏 3 个 required −150、1 次正确 report +100、扣均匀度）。
- 产物在 `runner/run_output/`：trace、decisions.csv（每次动作的指向/时长）、observation.csv（逐目标命中与得分）、score report。
- 打包提交：`cd python && python3 pack_agent.py --out <路径>` → 平台「参赛」页「新建提交」上传。模型 API 栏标"可选"但**评奖上必选**。

## 2. 时序与几何（易误解点）

- slot = 900 秒，**对齐 UTC 整 15 分钟**（00/15/30/45），不是从观测开始起算；跨昼夜边界的 slot 直接丢弃，只保留完全在黑夜内的 slot。
- 黑夜界线：太阳高度角 −18°（`sun_altitude_limit_deg`，全比赛不变）。
- `minimum_altitude_deg` = 30：曝光全程不低于 30° 的目标才计分，掉下去的目标**白白浪费曝光**（讲座特别强调）。
- `utc_offset_hours` 只用于读本地时间，天球计算直接用 UTC（否则重复引入时差）。
- 光纤网格编号：从下到上、从左到右递增，`id = grid_side × row + col`（示例 4r+c）。

## 3. 示例代码架构（kit/python/）

- `agent.py` 入口：后端直接 `python3 agent.py` 拉起；解析 initialize → 存全局 state → 按消息类型分支。
- `geometry.py`：天球位置公式（可与指南公式 1–16 对照检查）。
- `scoring.py`：评分函数——**含未乘天气因子的理想分**，与系统反馈的实际分对比即可反推某方向天气好坏、该选 DARK 还是 BACKUP（重要技巧）。
- `planner.py`：决策中枢；示例中大模型只承担 `night_advice`（每晚观测/避开哪些天区）一个角色，通过 `llm_client` 调用。
- `memory.py`：决策写入 `AGENT_TRACE_PATH` 指定的 trace.jsonl 便于复盘。
- `validation.py`：每次动作后校验协议与天气限制，可自行加强；`protocol.py` 不需要改。
- **零基础上手路径：先改 `night_advice`**（如把"避开整个有云扇区"升级为"只避云区边缘+试探性观测"）。

## 4. 计分理解要点

- 每次观测结束后系统反馈各 target 本次得分——用来核对预期、判断命中。
- report：正确 +100；错误容忍度每卡不同（1–3 次免罚，以卡 config 为准），超后每次 −150，下一次正确举报才清零重计。
- 同一目标只记最高分：天气好时可给老目标"刷分"，是 agent 的主动抉择点。

## 5. 讲者给的优化方向

1. 按周/月复盘：已观测 target 及 best score、剩余目标、当前均匀度罚分、未来预报 → 决定后续观测片区。
2. 快速摸天气：天气只有描述文本无数值；每晚/每 slot 开始用短曝光试探 + 理想分对比法反推。
3. 重观测权衡：窗口紧的目标优先，天气好时给高权重目标刷分。
4. 均匀度：结合公式周期性计算当前 J，引导未来天区。
5. 架构实验：极简（薄封装 + 工具脚本）vs 极繁（分层状态机+严格校验），看性能差异。
6. 防过拟合：可写随机天气播报脚本（按协议每 15 分钟发消息）在本地生成无限天气场景训练。

## 6. 答疑（官方口径）

- **依赖安装不计入 900 秒**，只算正式交互开始后的墙钟。
- **LLM 要求**：官方倾向"实际调用"（部署不调不算使用）；评奖看 ≥2 环节 LLM 驱动。
- **模型选型**：不同 base model 差异不大，甚至小于同模型跑两次的差异；关键在 harness/边界约束设计（这正是考核点）。强模型更多在设计阶段给 insight。
- **Kimi 使用**：直连非中转；避免 k3 的 max 慢速强档（用高速档）；比赛期间若 Kimi 挂了会换供应商。
- **API 不稳定补偿**：agent 内把连接报错/HTTP 日志 print 出来、zip 里附 README 写明日志位置；若因供应商时延导致没跑完，组委会读日志核实后**补偿 1–2 次机会**。
- **评测次数**：已扩容，会给更多次数；资源允许会多放留出出错空间。
- **决赛卡**：完全不公开的 4 套题（3 简单 + 1 难，同构仅数据不同），非交互式、不实时出分，赛后公布全部日志、排名与卡片文档。
- **运行环境**：国内服务器（GitHub Actions，依赖在国外；有国内刚需后续可能调整）。
- 非技术表态：环境本身不完美，把自身一端做强（harness 支持 loop/重启/断点续跑）。

## 7. 转写存疑项（勿轻信）

- 曝光时长上限：转写混乱（"60 到 300 到 3600"），收尾明确为 **3600 秒**——与文档一致。
- 亮度零点区间、"9900 秒"等数字均为转写错误（应为 0.3–0.4、900 秒）。
- Kimi 档位名（k3 max / high-speed / 2.7/2.8）转写不清，以 Kimi 官方文档为准。
